- **v51 (2026-08-19)** — Follow-up to v50, and a real bug the cutover introduced that was caught before it bit. Serving `data/catalog-cache.json` from the function bundle means the endpoint's data now refreshes **only on deploy**; the Blobs version did not, so nothing in the deploy path had ever needed to care about `data/`. `scripts/netlify-ignore.sh` decides whether a push is worth a deploy, and `data` was not on its watched list. `.github/workflows/scheduled-sweep.yml` commits `data/catalog-cache.json` and nothing else, every Sunday, so the very next sweep would have matched no watched path, skipped the deploy, and left `/api/catalog-cache` serving whatever JSON was bundled at the last unrelated deploy. Nothing would have gone red: the sweep runs, the commit lands, the served cache silently freezes, and the only alarm is `concert-radar-health-check.mjs`'s 9-day freshness check, which would have blamed the sweep rather than the skipped deploy. Fixed by adding `data` to the watched paths. `scripts/test-netlify-ignore.mjs` (new, 6 assertions, wired into `npm test`) runs the real ignore script against a throwaway git repo and asserts its actual exit codes for a sweep-only commit, a Function change, a page change, a docs-only commit, a backups-only commit, and a cleared build cache. Note that the ignore script's own header already anticipated this exact case in its `backups/` judgment-call paragraph, written months earlier: "if backups/ is live data your site or functions read at runtime, change the exclude line." `data/` became that case and the note was the one that mattered.

- **v49 (2026-08-19)** — JamBase attribution compliance closed, after being carried as an open risk since 2026-08-13. The blocker was never the fix, it was the doc: `data.jambase.com/api/docs/attribution` is client-side rendered, so three consecutive sessions' fetch attempts returned page metadata and no body text, and v21.1 shipped a clearly-labelled placeholder rather than guessing. Read this session in a real browser.
