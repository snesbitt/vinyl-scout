A catalog that looks after itself

This site's catalog has been lost twice — once to a bad edit, once to a broken deploy. Both times it was back within a day, because a set of small automated jobs had been built around it with Claude. None of it required writing code by hand. The same recipe works for books, watches, wine, or trading cards.

01Start with the data

Tell Claude what you collect and which fields matter — condition, year, what you paid, what it's worth now. From that description it can build a spreadsheet or a small site like this one. An existing messy list is a fine starting point; cleaning it up is the kind of chore Claude handles well. Plan on an afternoon, most of it spent entering items.

02Add market prices

A scheduled task — a saved instruction that runs on its own, weekly in this case — looks up marketplace prices through a small server function that talks to Discogs (eBay sold listings cover most other hobbies) and stores low, median, and high next to each item. The catalog header now shows a running total, around €2,200 at the moment.

Expect a few bad matches in the first runs. Each one needs to be pointed at the right listing once; after that they stay fixed.

03Nightly backups

Every night, a function commits the full catalog as a dated JSON file to the site's GitHub repository — the same place the code lives. Recovery after the second data loss consisted of pasting the previous day's file back in: about ten minutes of work.

04A daily health check

The last piece is a daily check that only reads, never writes. It counts the records, verifies the prices are still present, confirms last night's backup landed in GitHub, and compares the live catalog against it. When everything is fine it reports one line. When something is off, it says what's missing, what it expected, and which file to restore from. It deliberately has no ability to change anything — repairs stay manual.

05What it runs on

The plumbing is deliberately ordinary. The code lives in a plain GitHub repository, and pushing a change there is the entire deploy process — Netlify notices the push and rebuilds the site in under a minute. Netlify also hosts the records in its storage and runs the small server functions: the public API, the Discogs price lookup, and the nightly backup that writes back into GitHub. Every piece is free-tier, and none of it is precious — any part could be swapped out without touching the rest.

06Chat, terminal, Cowork, or a schedule

"Built with Claude" means four different modes, and knowing which to reach for saves real time. Chat is for deciding: which fields to track, which grading system to use, drafting text like this page. The terminal (Claude Code) is for building: the app itself — the API, the storage, the backup function — was written there, session by session, with the owner reviewing each deploy. Cowork is for maintaining: it works with files and a browser, and it committed this very page to GitHub and adjusted the gallery layout without a terminal ever being opened. Scheduled tasks are for repeating: anything you'd otherwise have to remember to do nightly or weekly. A feature typically moves through all four, left to right.

07Notes from running it

Build in the order above — each step is useful even if you stop there. And expect the early stretch to be slower than the pitch. For the first months of this project, most of the time went into debugging: a new feature would arrive with mistakes in it, fixing one thing would quietly break another, and every fix meant publishing the site again just to test it. Both catalog losses date from that period.

Two changes shortened that loop more than anything else: moving the day-to-day work into Cowork, and newer versions of Claude — this page was written and shipped by Fable. Changes now tend to work on the first try, and they get checked on the live site before being called done. What used to be an afternoon of back-and-forth is usually minutes, and the daily check has mostly had quiet mornings to report since.

The rest of what we'd pass on: make one small change at a time, so when something breaks you know exactly what caused it. Keep the automatic jobs read-only — on this site, the jobs allowed to write are the ones that have caused incidents. Write down how the whole thing works on a page like About, because every new working session starts by reading it. And accept that the first version of anything will be wrong in some small way; the backups and the daily check exist so a mistake costs a day, not the collection.
