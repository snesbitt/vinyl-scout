A personal vinyl catalog, built and run by an AI agent

Six steps to a system of record built on the same principles that govern data at any scale: accountability for what is collected, verification that it remains accurate, and a defined path to recovery when it doesn't. Follow them in sequence — each stands on its own — and the same architecture holds for books, watches, wine, or shoes.

Field note

This system has failed twice — once through a bad edit, once through a broken deploy — and both times was recovered within a day, because the governance layer described below was already in place before it was needed. Build all six steps. Trust in a system isn't restored by the steps you found interesting; it's restored by the ones you were tempted to skip.

01Match the tool — and the model — to what the job requires

Four operating modes, four distinct responsibilities — the same separation of duties that governs any well-run data function, scaled down to one person and one collection. Chat is where decisions get made: which fields to track, which grading standard to apply, how to describe the thing in language a reader can trust — this page among them. The terminal (Claude Code) is where the system gets built: the API, the storage layer, and the backup function were all written there, and every deploy was reviewed before it shipped. Cowork is where the system is maintained day to day — it operates on files and a browser, and it shipped this very page without a terminal session ever opening. Scheduled tasks carry the responsibilities no one should have to remember: the weekly price refresh, the nightly backup, the daily integrity check. A capability typically moves through all four in sequence, left to right, gaining a layer of accountability at each stage.

Mode determines where the work happens. A separate, equally deliberate decision determines how much model that work warrants — not every task carries the same risk, and assigning more capability than a task requires is resource spent without a corresponding return. Four tiers, ordered roughly by what they cost to run:

Haiku

routine · read-only · high frequency

The right tier for low-risk, high-frequency work that requires little judgment and produces no side effects. On this system it runs the nightly backup and the daily integrity check — jobs that need to execute reliably, not creatively.

Sonnet

the default

The appropriate baseline for the majority of the work: an API endpoint, an ordinary bug fix, a standard Cowork session. Most of steps 02 through 06 below were built at this tier. Absent a clear reason to move up or down, this is where the work belongs.

Opus

hard problems · high stakes

Reserved for decisions where an error carries real cost, or where the reasoning genuinely spans several dimensions — a schema decision, a defect that crosses multiple files. The no-bulk-delete rule below was established at this tier, in the direct aftermath of a data-loss incident.

Fable

narrative & prose · public-facing

For language a real audience will encounter — a guide such as this one, a public-facing page. Unnecessary for the infrastructure itself: a system like this runs predominantly on Sonnet and Haiku, and calls on Fable only for the rare page meant to be read, not run.

The governing principle: default to Sonnet. Step down to Haiku for anything scheduled or read-only, where the efficiency compounds over time. Step up to Opus when the cost of error is meaningful. Reserve Fable for the writing that represents you publicly, not the code operating quietly underneath it.

02Establish the data foundation

Define, at the outset, what is being collected and which attributes actually matter — condition, year, purchase price, current worth. That definition is the foundation everything downstream stands on; from it, Claude can build a spreadsheet or a small site like this one. An existing list, however disorganized, is an entirely adequate starting point — the cleanup itself is straightforward work. Budget an afternoon, most of it spent entering items, not designing the schema.

03Bring in an external valuation feed

A scheduled task — a standing instruction that executes weekly without intervention — retrieves marketplace prices through a small server function connected to Discogs (eBay's sold-listings data serves the same purpose for most other collecting categories), and records a low, median, and high figure against each item. The catalog's running total currently stands at roughly €2,200 — a number that carries weight only because the process behind it is verifiable.

Expect a handful of mismatches early on. Correct each one against the right listing a single time, and the correction holds.

04Build recoverability into the system

Every night, a function commits the complete catalog as a dated JSON file to the same GitHub repository that holds the code. Recovery is not theoretical: after the second data-loss incident, restoring the collection meant pasting the previous day's file back in — a process that took about ten minutes.

05Institute a daily integrity check

The final safeguard is a daily check that reads and never writes — a distinction that matters more than it sounds. It counts the records, confirms prices are present, verifies that the prior night's backup landed in GitHub, and reconciles the live catalog against it. When everything holds, it reports a single line. When it doesn't, it states precisely what is missing and which file to restore from. It has no authority to alter anything itself — remediation stays a human decision.

06Keep the infrastructure ordinary, and accountable

The infrastructure is deliberately unremarkable. The code lives in an ordinary GitHub repository, and pushing a change there constitutes the entire deployment process — Netlify detects it and rebuilds the site in under a minute. Netlify also hosts the records and runs the server-side functions: the public API, the Discogs lookup, and the nightly backup that writes back into GitHub. Every component runs on a free tier, and none of it is treated as irreplaceable — the resilience comes from the process, not from any single piece surviving.

Field notes

What we would advise

Build in this order — each step stands on its own. The early period ran slower than any pitch implies: most effort went into debugging, one fix breaking another, each fix demanding a fresh deploy to confirm it. Both data-loss incidents date from that period.

The discipline that matters most: change one thing at a time, so failure has a traceable cause. Keep every automated job read-only — every incident here traces to a job that could write. Document how the system works, as on About. Expect the first version of anything to be wrong; backups and the daily check exist so a mistake costs a day, not the collection.
