Six steps to an accurate collection inventory

Know what you have. Check it's still accurate. Know how to recover it when it's not. Build the six steps below in order. Each one works alone, and the same steps hold for books, watches, wine, or shoes.

This page is the how-to: the method and the exact prompt to build a catalog like this yourself, for any collection. For what this specific catalog does today: its data model, its feature set, its stack. Read About instead.

01Match the tool to the job

Four modes, four jobs. Each one earns more accountability than the last. Chat decides: which fields to track, which grading standard to apply, how to describe things in language a reader can trust, this page included. The terminal (Claude Code) builds: the API, the storage layer, and the backup function were all written there, and every deploy gets reviewed before it ships. Cowork maintains: it operates on files and a browser, and it shipped this very page without a terminal session ever opening. Scheduled tasks repeat what no one should have to remember: the weekly price refresh, the nightly backup, the daily integrity check. A feature moves through all four in sequence, left to right, gaining a layer of accountability at each stage.

The four modes above answer where the work happens. A second, separate decision is which version of Claude does it: Claude comes in a few strengths, each priced differently, and the job is to match strength to stakes, not default to the biggest one out of habit. A scheduled, unsupervised job like the nightly backup gets the fastest, cheapest version, since nothing is watching and nothing needs extra judgment. Ordinary building work gets the standard version. A problem where a wrong answer would actually cost something, real data, real money, gets the strongest version available. 02Define the data first

Decide upfront what you're tracking and what actually matters: condition, year, price paid, current value. Everything downstream (a spreadsheet, a small site like this one) gets built from that one decision. A messy list is a fine starting point; the cleanup itself is the easy part. Budget one afternoon. Most of it is entering items, not designing the schema.

03Pull real market prices, on a schedule

A scheduled task runs weekly, unattended. It pulls prices from a real source for the category (Discogs here; eBay's sold listings do the same job for most other collecting categories) and logs a low, median, and high figure for every item. This catalog's running total: about €2,200, a number that carries weight only because the process behind it can be checked.

Expect a handful of early mismatches. Fix each one against the right listing, once. The fix holds.

04Back it up automatically, every night

A scheduled task saves the complete catalog as a dated file, into the same GitHub repository that holds the code. This isn't theoretical: after the second data-loss incident, recovery meant pasting the previous day's file back in. Ten minutes. Done.

05Check it daily: read-only, always

The final safeguard is a daily check that reads and never writes, a distinction that matters more than it sounds. It counts the records, confirms prices are present, verifies the prior night's backup landed, and reconciles the live catalog against it. It has no authority to change anything itself; fixing it stays a human decision.

06Keep the plumbing simple

Ordinary GitHub repository. Push triggers the whole deploy. Netlify rebuilds in under a minute, hosts the data, and runs the background jobs: the Discogs price pull, the nightly backup. Every piece runs on a free tier. Nothing is irreplaceable. The diagram below is the whole system.

Build your own · a starting point

Copy this prompt to start

This system started from one written request to Claude, then grew in stages: a live pricing feed, nightly backups, a daily integrity check, every irreversible step held for approval along the way. Below is a version of that starting request. Copy it, adapt it to your own collection, and paste it into a new Claude conversation. 

I want to build a personal catalog for my collection (records, books, watches, wine, sneakers, or whatever I actually track), with a running estimate of what it's worth.

Here's the pattern I want it to follow:
1. Start from whatever list I already have, however messy, and help me turn it into a clean, structured record: one field per attribute that actually matters (condition, year, what I paid, current value).
2. Pull live market prices on a schedule from a real source for my category (a marketplace's sold listings, an auction index, whatever fits), so the value stays current without me pricing anything by hand.
3. Publish it as a small, real website I can check from my phone.
4. Back the whole catalog up automatically every day, somewhere separate from the live copy, so a bad edit or a broken deploy costs a day, not the collection.
5. Run a daily check that only reads and verifies (record count, prices present, backup landed) and tells me plainly if anything's wrong, without ever giving it the authority to fix anything itself.
6. Treat any bulk delete or destructive edit as something that always needs my explicit yes, no exceptions.

Please help me scope this into a first small version we can finish today, tell me exactly what you'd need from me at each step (any account access, any purchase like a domain name, anything you can't do without my say-so), and don't do anything irreversible without checking with me first.

How this actually gets maintained

All of this runs inside Cowork, working from a single project folder Claude keeps on your behalf: the code, the data, and a file called CLAUDE.md, Claude's own running notes on how the system works, decisions already made, and what's still open. Every new Cowork session reads that folder first, so it picks up exactly where the last one left off, and writes its notes back before it ends. You never have to re-explain the project from scratch, even months later.

Worth knowing before you start

Build in nightly backups and a daily health check from day one. They're the cheapest insurance you can add to a project like this, and far easier to set up before you need them than after. This exact catalog's own backup and check have already turned what could have been a real loss into a ten-minute fix.

Field notes

What building this taught us

Build in order. Each step should stand on its own. The pitch is never the slow part, debugging is: one fix breaks another, and every fix needs its own deploy to prove it held. Both data-loss incidents happened right there, mid-debug.

Change one thing at a time. That's the rule that matters, because it gives every failure exactly one traceable cause, and every incident here traces back to a job that could write when it should have only read. Keep the system documented as you go, the way About stays current here.

Expect version one to be wrong: that's what backups and the daily check exist for. A mistake should cost a day. Never the collection.
