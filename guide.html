A catalog that looks after itself

Six steps to a catalog with an agent running it — pricing itself, backing itself up, and flagging when something's wrong. Follow them in order; each is useful on its own. The same recipe works for books, watches, wine, or shoes.

Field note

This catalog has been lost twice — once to a bad edit, once to a broken deploy — and back within a day both times, because the automation below already existed. Build all six steps, not just the fun ones.

01Pick your tools — and size the model to the job

Four modes, four jobs. Use Chat to decide what to build — which fields to track, which grading system to use, drafting text like this page. Use the terminal (Claude Code) to build it — the API, storage, and backup function were all written there, reviewed before each deploy. Use Cowork to maintain it day to day — it works with files and a browser, and shipped this very page without a terminal ever opening. Use scheduled tasks for anything you'd rather not remember — weekly price refreshes, nightly backups, the daily check. A feature typically moves through all four, left to right.

The mode decides where the work happens. Separately, decide how much model it needs — not every task deserves the same horsepower, and running routine jobs on a heavier model than they need is cost and time spent on nothing. Four tiers, roughly in order of what they cost to run:

Haiku

routine · read-only · high frequency

Fast and cheap — right for anything that runs on its own and doesn't need much judgment. On this project it runs the nightly backup and the daily health check.

Sonnet

the default

The right starting point for almost everything: an API endpoint, a typical bug fix, a normal Cowork session. Most of steps 02–06 below were built at this level. Default here unless a task clearly needs more or less.

Opus

hard problems · high stakes

Reach for this when a mistake would be expensive or the reasoning is genuinely hard — a schema decision, a bug that crosses several files. The no-bulk-delete rule below came out of a conversation at this level, after a data-loss incident.

Fable

narrative & prose · public-facing

For words a real audience will read — a guide like this one, a product page. Not needed for the plumbing: a project like this one runs mostly on Sonnet and Haiku, and reaches for Fable only on the rare page meant to be read, not run.

Rule of thumb: default to Sonnet. Drop to Haiku for anything scheduled or read-only, where the savings add up. Reach for Opus when getting it wrong would be costly. Save Fable for the writing that represents you, not the code running quietly in the background.

02Start with the data

Tell Claude what you collect and which fields matter — condition, year, what you paid, what it's worth now. From that it can build a spreadsheet or a small site like this one. An existing messy list is a fine starting point; Claude handles the cleanup well. Plan on an afternoon, mostly spent entering items.

03Add market prices

A scheduled task — a saved instruction that runs weekly on its own — looks up marketplace prices through a small server function talking to Discogs (eBay sold listings cover most other hobbies), and stores low, median, and high next to each item. The catalog header shows a running total, around €2,200 at the moment.

Expect a few bad matches at first. Point each one at the right listing once, and it stays fixed.

04Automate nightly backups

Every night, a function commits the full catalog as a dated JSON file to the same GitHub repository the code lives in. Recovery after the second data loss was pasting the previous day's file back in — about ten minutes.

05Build a daily health check

The last piece is a daily check that only reads, never writes. It counts the records, verifies prices are present, confirms last night's backup landed in GitHub, and compares the live catalog against it. Fine, and it reports one line; off, and it says what's missing and which file to restore from. It has no ability to change anything — repairs stay manual.

06Keep the plumbing ordinary

The plumbing is deliberately ordinary. The code lives in a plain GitHub repository, and pushing a change there is the entire deploy process — Netlify notices and rebuilds the site in under a minute. Netlify also hosts the records and runs the server functions: the public API, the Discogs lookup, and the nightly backup that writes back into GitHub. Every piece is free-tier, and none of it is precious.

Field notes

What we'd pass on

Build in the order above — each step is useful on its own. Expect the early stretch to be slower than the pitch: for the first months, most of the time went into debugging, one fix quietly breaking another, every fix meaning a fresh deploy just to test it. Both catalog losses date from that period.

Two changes shortened that loop more than anything else: moving day-to-day work into Cowork, and newer versions of Claude — this page was written and shipped by Fable. Changes now tend to work the first try, and get checked live before being called done. An afternoon of back-and-forth is usually minutes now, and the daily check has had mostly quiet mornings since.

The rest: make one small change at a time, so when something breaks you know what caused it. Keep automatic jobs read-only — on this site, every incident traces back to a job that could write. Write down how the whole thing works on a page like About, since every new session starts there. And accept the first version of anything will be wrong somehow; the backups and daily check exist so a mistake costs a day, not the collection.
